## 先说清楚，我们在聊什么

这两年 agent 这个词用得有些泛滥。几句话之内，模型、框架、agent、harness 就容易被混为一谈。进入机制之前，先把三个概念分开。

**模型，是一个无状态的推理函数。** 输入一串 token，输出一串 token，下一个 token 由概率决定。模型权重不会因为对话而改变，相同输入面对的是相同的概率分布，上一轮调用不留任何状态。它不能访问文件，也不能访问进程。产品中表现出的记忆，无论是跨会话记忆还是历史对话，都不存在于模型内部，而是由外层系统存储、在下次调用前重新拼入输入，这部分在第 4 篇展开。模型本身不是 agent，只是一个零件，并且会在判断错误时仍然给出高度确定的表述。

**Harness，是包裹在模型之外的整套工程。** 下一步动作如何决定，上下文装配什么、舍弃什么，工具如何调用，命令在何处执行，危险操作由谁审批，历史如何存储、中断后如何续接，界面如何呈现，都在这一层。模型表现出的 agent 行为，全部由这层壳安排。本系列讨论的内容，几乎都在壳这一层。

**环境，是 agent 作用的世界。** 文件系统、shell、git 仓库、浏览器、网络、其他服务，以及人。

三者之间有三条边界。

需要说明，这三条边界不是官方术语，而是我拆解这类系统时使用的分析框架，换一种划分同样成立。划分依据是：模型被隔离在壳内，自身不能接触外部，只能通过出口产生作用；出口之外只有三类对象，信任关系各不相同，继续合并会丢失信息。

- **推理边界**，harness 到模型的一次 token 往返。边界另一侧是模型，是唯一输出具有概率性的对象，返回结果不可预设。系统的不确定性只从这一处进入，重试、降级与预算控制都针对它。
- **副作用边界**，harness 到环境，即工具实际执行的位置。另一侧是文件、网络和其他服务，状态确定、可被改变，且通常不可逆。进程外部的状态只有经过这条边界才会改变，沙箱与审批都设置在这里。
- **人本边界**，人与 harness 之间。另一侧是人，持有最高授权并可随时中断。指令可以下达，但最终授权不转移。

之所以是三条而不是两条或五条：把模型并入环境，会丢失“概率接缝只有一处”这一关键信息；把文件和网络进一步拆分，二者信任关系相同，不增加信息。后续每一篇基本对应其中一条边界。实际链路会跨越多条边界，例如一次工具调用由模型选择、harness 执行；划分边界是为了理解结构，并不意味着各部分互不相干。

范围也在此说明：模型训练、权重、推理内核、GPU 调度不在本系列内，也不讨论提示词技巧。本系列只回答一个问题：**把一个模型做成能实际完成工作的系统，需要哪些工程。**

## 和传统软件工程，差在哪

我的基本判断是：harness 中九成是传统软件工程；剩下一成的难度，不在于工程更复杂，而在于系统中“下一步做什么”这一控制环节，从确定性程序变为概率模型，并由此引发一系列连锁变化。

抽象论断不够直观，下面拆解一个工业级 coding agent。图 2 依据 OpenAI 开源的 codex 模块结构整理，该项目用 Rust 编写，包含一百多个 crate，是目前可见的较完整样本之一。

<figcaption>图 2 · 工业级 Harness 的模块分类图（据 codex 的 crate 结构整理，灰橙红浅绿四根立柱按与模型的关系分类）</figcaption>
</figure>

四根立柱：

- **灰色，九成底盘。** 界面、网络代理、密钥、文件与 git、安装包。这些模块与 LLM 无关，沿用既有工程方式实现。
- **红色，新产生的一成。** turn 循环、上下文、指令层级、工具结果回灌、决策回放，在传统软件中没有对应物。
- **浅绿，传统工程的新位置。** 模型网关、协议适配、事件存储，以及同一内核同时支撑 CLI、IDE 与云端。它们围绕 LLM 构建，但真正的难点在限流重试、故障切换与版本兼容，与概率无关。
- **橙色，最容易被误判的部分。** 位于传统区域、承担传统职责，但契约已被概率改变，单独说明。

橙色立柱中的几个模块，过去都很熟悉：

- 沙箱过去防御外部攻击者，现在需要防御 agent 自身；它并非恶意，而是会真诚地认为某一步应当执行 `rm -rf`；
- 命令执行器过去接收人输入的命令，现在接收模型生成的字符串，命令注入面与进程挂起的处理都随之改变；
- 配置过去是 YAML 这类形式语言，现在 AGENTS.md 是自然语言，失效方式也不同；
- 日志与指标过去用于定位报错位置，现在还需要用于还原模型当时为何做出某一判断。

老模块，新契约。图中将这一条称为污染带。

根因可以概括为一句：

> 传统系统的控制流可以枚举；在 agent 中，“下一步做什么”交给了一个概率函数。

设计目标因此改变：过去要求接口正确，现在必须保证 **即使模型理解错误，系统仍然安全、可恢复、可观测**。后续每个红色与橙色模块的设计，都可以追溯到这句话。

## 这个系列打算怎么写

主线是一次 turn 的生命周期，从按下回车到任务结束，逐环拆解。研究对象是两个开源仓库：codex（Rust，工业级、完整）与 opencode（TypeScript，另一种实现风格）。每篇大致采用同一结构：一个核心问题，两个实现对照，关键代码切片，配一张图。

计划中的篇目：

1. 一个 turn 的一生——回车之后到底发生了什么
2. 内核循环：规划、反思，和一个可能停不下来的状态机
3. 模型边界：协议、限流、故障切换与成本
4. 上下文与记忆：寄存器、内存和磁盘
5. 工具与执行：模型怎么真正动手
6. 沙箱与信任边界：防的是自己人
7. 指令层级：用自然语言编程
8. 扩展生态：MCP、hooks、plugin 各是什么
9. 一副内核多副面孔，以及多智能体
10. 概率系统怎么测；收口：造 Harness 的几条原则

顺序与篇目会在写作中调整。

我做了十几年后端与平台，写这个系列也是一次梳理：在 agent 相关工程中，哪些是既有工程能力的迁移，哪些是此前没有遇到过的新问题。把这两者分清楚，比追踪新名词更有价值。
